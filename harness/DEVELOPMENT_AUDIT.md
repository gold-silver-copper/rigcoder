## One next experiment: isolated task-network feasibility

**Hypothesis:** the existing host-owned model relay can support useful coding execution while the candidate cannot obtain benchmark answers through arbitrary external network access. The smallest next step is a measurement, not a broad sandbox rewrite. The audit establishes a concrete evaluation gap but not a safe, effective full-dev runtime candidate.

**Before/after to investigate:** today ordinary trials get network access and a direct model key; arbitrary Python/curl commands can fetch public answers. The candidate design would route only model traffic through the host relay while task networking follows a host-enforced policy. A prompt or tool-command deny list is not enforcement. Preserve task instructions, verifier behavior, timeouts, model, and tool semantics.

**Bounded offline scope:**

1. Using the existing benchmark and development task images only, inventory runtime package/data downloads and local-service requirements across all twenty dev tasks. Classify observed accesses as required, optional, answer acquisition, or unresolved. Do not inspect holdout tasks. Do not preinstall new task dependencies, edit images/tasks, or silently change the evaluated problem to make isolation pass.
2. Extend the existing synthetic relay canary to test rejected arbitrary outbound requests through shell/Python, direct IP and redirects, while mocked model completions and required loopback services still work. Use synthetic endpoints and fake secrets, not real answer URLs. Record container image/network identity and every probe outcome. Do not launch actual task-model completions.
3. Produce a per-task compatibility matrix and one minimal integration proposal using the existing runner. Stop at measurement if required downloads cannot be supported without opening answer access or altering tasks. Reject a broad domain allowlist that admits public benchmark repositories, a tool-text filter, or any bypass of the current scorer eligibility guard.

Relevant implementation locations are [docker.rs](../crates/rigcoder-bench/src/docker.rs) (`start_with_network`, L103), [trial.rs](../crates/rigcoder-bench/src/trial.rs) (`execute`, L134; ordinary verifier installation, L430), [trial_relay.rs](../crates/rigcoder-bench/src/trial_relay.rs), [evolve.rs](../crates/rigcoder-bench/src/evolve.rs) (host-scoring eligibility, L487), and [the relay canary](check_gemini_relay_docker.py). Do not add another runner. The current `--gemini-budget` path supports only declared host scorers; ordinary dev tasks use in-container `test.sh`. Network isolation alone also does not establish scoring isolation, since ordinary scoring executes in the candidate-modified container. Report this as an unresolved boundary, not a solved property.

**Offline acceptance:** all synthetic blocked-access probes are denied, mocked provider requests succeed with keys outside the candidate, loopback checks succeed, no unknown accounting is treated as zero, and every dev task has an explicit compatibility determination. Any required task capability that cannot be preserved rejects immediate full-dev rollout. Passing the canary alone does not pass this gate.

**Conditional paid evaluation design, not authorization:** only after the compatibility and scoring boundaries are established and spend reconciled, compare a frozen baseline and the single candidate in existing `rigcoder-bench run`. Pin source-input hashes, agent binary, task snapshot, images, prompt, model, 200-turn setting, concurrency and retry settings.
